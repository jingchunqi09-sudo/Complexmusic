# 控制路线（唯一真源）

日期：2026-11-02
> **编者注（开源包）**：本文写于 R39 / 固件 3.2.0。此后 R40~R59 未改动上下位机
> 寄存器表与帧格式（R54 的 README 明确写「没有动链路寄存器」），
> 因此**控制路线对 R54 仍然有效**，差异只在固件版本号（R54 配 3.5.10）。
> **本文未覆盖** R60 起新增的曲谱指引寄存器 `REG_GUIDE_CTRL/LANE/NOTE`（0x30~0x32）
> 与只读 `REG_PLUCK_CNT/MASK`（0x33/0x34）。

适用位流：**R39**（录音抽头移出发声路径；音频总线 fanout 与 R36 相同）
适用固件：**3.2.0**（沿用 R38，未改）

> 这份文档回答一个问题：**手机上动一个控件，信号究竟经过哪些环节、最后改变了什么。**
> 每一行都是照着 RTL 和固件逐条核对出来的，不是照协议注释抄的。
> 协议注释与 RTL 不一致的地方，以本表为准（并把差异写在 §5）。

> **R39 相对 R38 只改一件事：录音抽头不再碰 pcm。**
> R38 把 16 根 50 MHz 翻转的 pcm 网络送进链路模块，实板出现 S1/S2 随机自鸣
> （仿真逐样本相同，所以是物理层问题）。R39 改成从 `pt8211_tx.o_frame_pcm`
> （DAC 已装载的寄存器输出）取样，pcm 扇出回到 1，链路只收 9 根低频字节线。
> **代价：录音变成"音量之后"的信号。**

## 1. 总链路

```
手机浏览器 (WS:81 / HTTP:80)
        │  JSON  {"c":"vol","v":200} ...
        ▼
ESP32  3.1.0  main.cpp → link_v2.cpp:sendRaw()
        │  UART2 230400 8N1
        │  帧 = A5 5A | CMD | SEQ | LEN | PAYLOAD... | CRC16_L | CRC16_H
        ▼        （**载荷在前、CRC 在后**；CRC 覆盖 CMD..PAYLOAD，不含两个 SOF）
FPGA  E13(RX) → uart_rx → link_frame_rx（CRC 通过才 frame_valid）
        ▼
      cmd_dispatch（地址/数据映射表）
        ▼
      link_regs（48 字节参数表，上电默认值 = R24/R33 的硬编码常量）
        ▼
      各消费模块（见 §2）
```

**唯一不变式**：不插 ESP32 时，`link_regs` 的每一个复位值都等于 R24 里写死的常量，
所以「不接线」和「接线但一帧不发」声音完全相同。这条由 `sim/tb_link_boot.v` 守着。

## 3. 「不破坏正常演奏」的三条不变式

这三条是本轮所有改动的前提，也是以后加功能时必须守的红线。

**① 演奏总线不受 ESP32 影响。**
```
next_gates   = {4'd0, selected_strings & {4{bow_gate}}}   // 只由左手/压电/弓速决定
aud_note/gate/trigger/stop/speed/event                    // 全部直连物理前端
```
R33 起 `lane_arbiter` 不再例化，曲谱事件**没有任何一条线连到发声总线**。
所以「手机发什么」都不可能让某一根弦自己响。

**② 曲谱只驱动显示。**
事件进 `score_player` 后只被顶层锁存成 `g_lane/g_note`，再跨到视频域画指法框。
`tb_score_guide` 断言：上传 2 个事件并播放，`pcm_nonzero == 0`。

**③ 默认值逐位等于 R24。**
`tb_link_boot` 逐条比对 16 个参数 + 200 字节垃圾不产生事件；
`tb_top_rest` 静止 467 样本全 0，md5 `8a5b0d8d…` 与 R24 逐字节相同。

**④ 录音只读，而且不碰音频总线。**
```
dac_pcm = pcm                      // 唯一负载是 pt8211_tx，扇出 1
u_rec_tap.pcm = pt8211_tx.o_frame_pcm   // DAC 已装载的寄存器输出，单向、在下游
```
R38 的写法是 `rec_pcm_r <= pcm`，把 16 根 50 MHz 翻转的线拉进链路模块，实板 S1/S2 自鸣。
R39 把它换成从 DAC 的输出寄存器取样：**录音抽头物理上在 DAC 之后**，
`pcm` 的扇出、走线、翻转率与 R36 完全一致。

历史三次事故（R26 / R34 / R38）的共同点都是"把 pcm 引出去"，所以这条不变式是硬的：
**任何新增功能都不许在 pcm 上加负载。**

## 4. 固件改了什么，为什么

### 4.1 固件 3.2.0（配合 R38）

| 改动 | 旧行为 | 新行为 | 原因 |
|---|---|---|---|
| 录音网页提示 | 写死"当前位流（R36）没有开通录音，提示 no audio 是预期行为" | 改成按实测状态说话：提示只有 R36 及更早才会 no audio；并加"录音期间请勿拖动参数" | 文案会误导——R38 上录音真的能用了 |
| 版本号 | 3.1.0 | 3.2.0 | 用户需要知道该配哪版位流 |

**固件本轮没有改任何协议字段。** R38 的录音帧格式与 `rec_player.cpp` 里已有的解码器
完全兼容（这一点由 §6.4 的逐字节比对证明，不是靠"应该兼容"）。

> 关于「录音期间拖动控件」：`rec_stream` 与命令分发共用一个 64 字节发送缓冲，
> 同拍时 dispatch 优先。碰撞概率很低（录音每 2.7 ms 才占用 1.12 µs 的填充窗口，
> 而一条命令帧要 350 µs），但**一旦撞上就是丢一帧**，LADPCM predictor 会失步，
> 表现为后半段发糊。这属于「用界面约束代替 RTL 改动」的取舍：
> 在 RTL 里做互斥要动发送仲裁，风险远大于收益。

### 4.2 固件 3.1.0（R37 已交付）

| 改动 | 旧行为 | 新行为 | 原因 |
|---|---|---|---|
| 曲谱事件 lane | `gTimbre[s] ? s+4 : s` | 直接用 `s`（0..3） | 一旦点过"尤克里里"，事件发到 lane 4..7，而 GUIDE 只画 `lane<4` → **目标框消失** |
| 定弦写入 lane | `st.tim[s] ? s+4 : s` | 直接用 `s` | 同上，会写进另一组 lane，表现为"改了没用" |
| 静音 | 写 `REG_MUTE(0x16)` | 走音量：保存→`vol=0`→恢复 | `REG_MUTE` 在 DAC 直连后**无人消费**，按了没反应 |
| 音量 | 一次跳到目标值 | 每 2 ms 逼近一小步（步长 `|diff|/16`，钳 ±2） | FPGA 侧音量逐帧直算、无斜坡，跳几十级会有 click |
| 音色倾斜 | 松手才发（`onchange`） | 拖动实时发，服务端 60 ms 节流 | 调音时没有实时反馈 |
| 换乐器 | 静默成功（实际无效） | 明确返回 `not supported` | 不再骗人 |
| 录音 | 一直等 | 800 ms 无音频 → 停止并提示 | 避免"录完是空的" |

所有固件改动都在 `esp32_wifi_console/src/`。

## 5. 协议注释与 RTL 的已知差异（以 RTL 为准）

| # | 文档写法 | RTL 实际 | 影响 |
|---|---|---|---|
| 1 | `link_pkg.vh` 帧头注释 `[5+LEN] CRC16 low` | 正确：`P_DATA → P_C0 → P_C1`，载荷在前 | 我第一版测试台按"CRC 在前"组帧，帧全被拒 → 已修正 |
| 2 | `CMD_SET_SENS` 看似 `p[1]=低 p[2]=高` | `cmd_dispatch` 里是**交叉**的：n=1→地址 0x07(高)、取 `r_args[2]`；n=2→地址 0x06(低)、取 `r_args[1]` | 净效果 = `{pluck, 低, 高}`，与现有固件一致，不用改 |
| 3 | `REG_TONE_BRIGHT` 注释写「高架 1800 Hz」 | R20~R47 实际 1200 Hz；**R48 起改成 300 Hz**（低架同时改成 1200 Hz） | 仅注释错，行为正确；R48 已在 `timbre_shaper.v` 头部重写理由 |
| 4 | `CMD_SCORE_END` | `cmd_dispatch` 没有分支（走 default 回 ACK），FPGA 不校验事件流 CRC | 校验由 ESP32 自己做 |
| 5 | ACK 长度注释 2 字节 | 实际 **1 字节**（只有状态码） | 固件已按 1 字节解析 |
| 6 | `rec_stream.v` 注释写「R_PRIME 之后一拍 `r_q = mem[r_rp]`，正好是首字节」 | **错**。`r_q` 是同步读、比 `r_rp` 落后一拍，`R_FILL` 里 `tx_wr_data<=r_q` 与 `r_rp<=r_rp+1` 同拍，于是首字节被写两次、末字节发不出去 | R38 已修（读地址预取 `r_rp+1`）。实测证据见 §6.4 |
| 7 | `CMD_REC_CTRL` 与 `REG_REC_CTRL` 都是 `0x17`？ | **不是**。命令码是 `0x30`，`0x17` 只是寄存器地址 | 开发期测试台发 `0x17` 被当成别的命令，白查一轮 |

## 6. 验证

### 6.1 新增 `sim/tb_ctrl_route.v`（本轮关键）

照固件 `sendRaw` 的真实帧格式发帧，逐条断言寄存器落地：

| 命令 | 断言 | 结果 |
|---|---|---|
| `SET_VOLUME 200 / 0` | `o_volume == 200 / 0` | PASS |
| `SET_TONE warm=0x1A5 bright=0x7FF en=1/0/1` | 三个字段分别正确 | PASS |
| `SET_TUNING lane2=57, lane6=65` | 目标 lane 变、其它 lane 不动 | PASS |
| `SET_FX 200/30/2/0` | `wet/damp/tail/bypass` 全部正确 | PASS |
| `SET_EXPR depth=0x12345 rate=0x1020304 glide=500` | 三个 LE32 正确 | PASS |
| `SET_SENS pluck=100 deadband=0x1234` | 16 位拼接正确（交叉字节序） | PASS |
| `REG_WRITE 0x00 = 77` | `o_volume == 77` | PASS |
| **CRC 错帧** | 被拒，参数不变 | PASS |

结果：`PASS ctrl route (all commands land on the right registers)`。

### 6.2 回归（R38 重跑）

| 台 | 内容 | 结果 |
|---|---|---|
| `tb_link_boot` | 上电 16 个默认值逐条比对 + 200 字节垃圾不产生事件 | **PASS 40 checks** |
| `tb_ctrl_route` | 8 类命令逐字节落地 + CRC 错帧被拒 | **PASS** |
| `tb_pt8211_volume` | DAC 内部音量（128 直通 / 缩放 / 饱和） | **PASS 10 checks** |
| `tb_top_rest` | 静止 467 样本 | 全 0，md5 `8a5b0d8d…`（= R36） |

`rec_stream` 的修改只动读口地址，写口、计数、状态机、授权条件全部未变。

### 6.3 三态 pcm 对拍（R39 的核心证据）

新增 `sim/tb_top_play.v`。它用 **force 顶层内部演奏总线**（`notes/gates/speeds/velocities/triggers`）
让 lane0 空弦 G3 真的起振——不改 RTL，对 R36/R39 两份源码施加完全相同的激励。

| 状态 | 说明 | 样本数 | md5 |
|---|---|---|---|
| A | `LINK_PCM_TAP=0`，无录音（= R36） | 408 | `42e457af9b716676f0fcdc70a2c8c187` |
| B | `LINK_PCM_TAP=1`，无录音 | 408 | `42e457af9b716676f0fcdc70a2c8c187` |
| C | `LINK_PCM_TAP=1`，演奏中途发 `CMD_REC_CTRL(0x30)=0x03` 真开录音，取前 408 样本 | 408 | 与 A 逐样本相同（diffs = 0） |

C 的内部探针：`lad_bytes=101、stream_wr=56、stream_send=1`——
即 **LADPCM 真的在编码、UART 真的在发帧的那段时间里，DAC 输出仍然一个样本都没变。**

R39 与 R38 的差别不在这个表（两张表都是 diffs=0），而在**物理结构**：
R38 的 `pcm` 扇出是 2（`pt8211_tx` + `rec_pcm_r`），R39 是 1（只有 `pt8211_tx`）。
这正是 R38 仿真全绿、实板却自鸣的原因——**这张表证明不了物理层，只证明逻辑层。**

### 6.4 录音链路端到端（`scripts/verify_r38_rec.py`）

1. 测试台把 FPGA→ESP32 的 UART 字节按 230400/217 分频逐位采下来（79 字节）。
2. 解帧得 3 帧：`ACK(0x80) ×2 + REC_AUDIO(0xA0) ×1`，载荷 56 字节。
3. 测试台同时导出录音链**真正看到的 PCM 序列**（`i_rec_pcm`）。
4. Python **独立重写一遍 LADPCM 编码器**（照 `rec_ladpcm.v` 的规则，不复用 RTL 逻辑），
   喂同一段 PCM，输出与 FPGA 实际发出的 56 字节**逐字节相同**：

```
编码字节 md5 = 56fac417ac7a77d14e5d06b22d10dad9
RTL 字节   md5 = 56fac417ac7a77d14e5d06b22d10dad9
```

5. 再用固件 `rec_player.cpp` 的同一套规则解回来：112 个样本，SNR 17.30 dB。
   （R38 从 pcm 直接取时是 14.29 dB；R39 从 DAC 末端取，相位不同、起点更平缓，
   所以同一个解码器给出了略好的数字。两段都是**起振冷启动**，峰值只有 0.3% FS。）

**这个比对顺带抓出了 `rec_stream` 的 bug**：修复前，同一段数据发出的载荷是
`67 67 ca ba bb …`（首字节重复），而 RTL 自己的字节流是 `67 ca ba bb …`。
修复后两者逐字节相同。

固件侧：`pio run` 通过（见交付目录 `firmware.bin`）。

## 7b. 多模型评审结论

### R38 阶段（原文见 `多模型评审_录音回传.md`）

千问 `qwen3.8-max` + Kimi `kimi-k2.7-code`（账号可用最高；k2.8 无权限）。
DeepSeek 那次只返回碎片化 thinking，未收录。

**对预取修复**：两家都说没问题（`r_rp` 9 位自然回绕、R_IDLE 的陈旧 `r_q` 不会被消费，
下一帧经 R_PRIME 重读覆盖）。

**对"会不会自鸣"**：两家都说 17 个 FF 这个量级本身不会，但**布局布线重塑**可能让历史隐患
复现（千问原话："更可能是 TAP 保留逻辑后改变布局布线…优先怀疑波导反馈/PCM 路由被扰动"）。
这条无法在 RTL 层面完全反驳，所以**上板首查项 = 不演奏时有没有弦自鸣/底噪**，
且要观察它是否随 `i_volume` 同步变化（能区分是 DAC 前还是 DAC 后）。

**采纳**：
- 上电静音自检写进验收步骤第一条。
- 确认综合后 BSRAM 地址端口仍是 9 位（`mem[0:511]` 512×8，资源报告 +1 块，已核对）。

**明确拒绝**：两家都建议"每帧复位 LADPCM predictor"。**不采纳**——FPGA 侧编码器的
`pred/idx` 跨帧连续，解码器逐帧复位等于每 2.7 ms 注入一次瞬态。丢帧的正确处置是
整段重录，不是局部修补。

**已满足、无需改**：
- 千问要求"CRC 失败必须整帧作废，禁止半字节进解码器"——固件本来就是
  `if (got == cal) handleFrame(...); else crcCount++;`，且 LEN 不可信时整帧丢弃重同步。
- 千问建议的"黄金音频自检"就是本轮的 A/B/C 三态 md5 对拍。

**记为待办**：Kimi 建议对 DAC 音频路径做 Logic Lock/区域约束。要动 PnR 流程，收益不确定，
本轮不做。

### R37 阶段（原文见 `../r37_20261102/多模型评审_控制路线.md`）

两家对 **Q5（有没有影响正常演奏）都明确回答"没有"**：

## 8. 一个已知行为（不是 bug）

**停止指引后，屏幕上的目标框会保留最后一个音。**
这是 R33 刻意的：单音练习的曲谱只有 1 个事件，1 ms 就播完、`score_state` 立刻回 0，
如果那时清目标，框只会闪一下，根本没法跟弹。
想"停止即清空"就按 §7-2 加一行 RTL。

## 8. R48 补充：音色那一路的可闻度修正

用户反馈"通过 WiFi 调音色，变化幅度不明显，听不出来"。查下来不是链路问题
（`CMD_SET_TONE` → `0x2A..0x2E` → `timbre_shaper` 全程可通，`tb_link_tone` 端到端 4/4），
而是**两个搁架拐点都落在没有能量的频段**，且峰值归一化让补偿变成单向：

| 方向 | 旧版（600/1200，±9） | R48（1200/300，±12） |
|---|---|---|
| 暖 +6 dB @1.8 kHz | −4.63 dB | **−8.47 dB** |
| 暖 +6 dB @8 kHz | −5.62 dB | **−11.01 dB** |
| 亮 +6 dB @8 kHz | −0.64 dB | **+2.53 dB** |
| 亮 +6 dB @273 Hz | −5.76 dB | −4.80 dB |

**故障定位新手段**：固件 3.4.0 起每 0.5 s 用 `CMD_REG_READ` 读回 `0x2A..0x2D`，
网页"音量与音色"卡片显示 `硬件回读 warm=… bright=… ✓ 与滑杆一致`。
以后再遇到"调了没反应"，先看这一行即可把「帧没到」和「听感差异小」分开。

细节见 `00_首页_最新版本/R48_音色可闻度_20261102/README.md`。
